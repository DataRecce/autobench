asana002dbtpackage
A package update made tags optional — gate the tag models/columns with the existing using_task_tags var. It is a shape change, not a type mismatch (a cast has no surface here).
64% pass-rate
before → after
before — cast attempt / unconditional tag refs
-- treats it as a representation mismatch
select ..., cast(tag_field as timestamp) ...
from {{ ref('stg_asana__tag') }}   -- tag model assumed present
after — gate the optional resource
{% if var('using_task_tags', true) %}
  ... tag models / tag columns ...
{% endif %}   -- tags optional in the new package version
f1006 · f1006-harddata-modelingf1 standings
Season totals from cumulative race-by-race standings: aggregate with max(points), not sum. Don’t switch to latest-row/rank logic.
52% pass-rate
before → after
before — sums cumulative snapshots
select driver_id, sum(points) as season_points
from {{ ref('constructor_standings') }}
group by driver_id   -- double-counts cumulative rows
after — max over cumulative grain
select driver_id, max(points) as season_points
from {{ ref('constructor_standings') }}
group by driver_id   -- final cumulative total
airbnb009data-modelingcoverage
A row for every day was missing. Make the minimal subtractive edit: drop the narrowing date predicate, keep COUNT(*) byte-intact, add no cross-join.
69% pass-rate
before → after
before — narrows the spine + rewrites aggregate
with day_set as (
  select date_col from {{ ref('dimension') }}
  where date_col in (select distinct fact_date from fact)  -- narrows
)
select count(fact_date) ...   -- aggregate rewritten
after — drop predicate, keep count(*)
with day_set as (
  select date_col from {{ ref('dimension') }}     -- predicate DELETED
)
select count(*) ...   -- aggregate UNCHANGED, existing join kept
airbnb005 · airbnb007data-modelingper-key agg
A per-key metric rollup should be built from the fact and inner-join the dimension — don’t left-join the full dimension and emit zero-fact keys carrying NULL metrics.
89% pass-rate
before → after
before — left-join emits NULL-metric rows
select dim.key, agg.metric
from {{ ref('key_dimension') }} dim
left join fact_agg agg using (key)   -- zero-fact keys → NULL nps
after — driven by the fact
select dim.key, agg.metric
from fact_agg agg
inner join {{ ref('key_dimension') }} dim using (key)  -- zero-fact keys excluded
f1010-mediumdata-modelinglap times
Averaging that must “account for” pit stops: exclude the pit-stop laps before averaging — don’t keep them and subtract pit-stop duration.
73% pass-rate
before → after
before — keep + subtract
select track, year, avg(lap_time - pit_stop_duration) as avg_lap
from laps
group by track, year
after — filter category, then average
select track, year, avg(lap_time) as avg_lap
from laps
where not is_pit_lap     -- pit laps excluded first
group by track, year
ana-eng003data-modelingbuild / rename
A build/rename that doesn’t restrict columns must preserve every upstream column; apply only the named renames/keys. Don’t prune to a “relevant” subset.
94% pass-rate

after — preserve all, rename only

from {{ ref('stg_customer') }}

asana003dbttmp-tier rewire
Removing a tmp tier is a behavior-preserving rewire: inline the deleted tmp model’s exact SELECT, swap only ref→source, and reconcile before == after. Don’t re-derive a fresh select.
70% pass-rate
before → after
before — re-derives fresh (drifts output)
-- stg_entity.sql after deleting stg_entity_tmp
select id, name, created      -- a "reasonable" fresh subset → wrong shape
from {{ source('pkg','entity') }}
after — inline tmp body verbatim, swap FROM
select id,
       cast(name as varchar) as name,
       coalesce(created,'1970-01-01') as created,
       ... every column the tmp produced, unchanged ...
from {{ source('pkg','entity') }}   -- was ref('stg_entity_tmp')
f1001dbtsrc naming
When building src models, name each exactly src_<table> (bare prefix matching the raw table). Don’t fold the dataset namespace into the name. Restates the task’s own instruction.
82% pass-rate
before → after
before — namespace folded in (wrong)
-- models/src/src_f1_dataset__circuits.sql   ← WRONG name
-- stg ref: from {{ ref('src_f1_dataset__races') }}
after — bare src_<table>
-- models/src/src_circuits.sql   ← matches the raw table
-- stg ref: from {{ ref('src_races') }}
f1003-harddata-modelingtop-N consistency
A limit N without a tiebreaker is inconsistent only when a tie crosses the cutoff. Count it iff more than N rows reach the N-th value. A tie fully inside (or outside) the top N only reorders display.
87% pass-rate
before → after
before — flags any tie
-- marks "inconsistent" because two rows tie somewhere,
-- even fully inside the top N  → over-includes answers
after — tie must cross the cutoff
-- N-th value = V; inconsistent iff:
count(* where metric >= V) > N
-- ties entirely inside/outside the cutoff don't count

What kind of knowledge is each rule?

Classifying the rules by transferability decides what carries to a new benchmark. 6.5 of 10 are general data-modeling principles that should help on any SQL/analytics task; ~3.5 are dbt/Fivetran-stack scaffolding to re-derive per stack — not port verbatim.

Data-modeling

6 rules · transferable
  • Preserve the column set on build/rename
  • Spine / coverage completeness
  • Per-key aggregate: inner-join from fact
  • max() over cumulative snapshots
  • Exclude a category before averaging
  • Top-N “tie-crosses-cutoff” criterion

dbt / Fivetran tooling

3 rules · stack-specific
  • Tmp-tier ref→source rewire (the inline half)
  • Package optional-resource var-matrix
  • src_<table> staging-layer naming

Mixed

1 rule
  • Feature-boundary removal — the concept (drop feature-only outputs, keep base FKs) is data-modeling; the expression (unwrap Jinja {% if var %} guards) is dbt-specific.
Porting rule for a new benchmark: seed the README with the 6 data-modeling principles in their distilled form; re-derive the tooling rules from the new stack’s conventions. The reconcile half of the tmp-tier rule (before == after, double-entry) is the most transferable single idea — it lets a refactor carry its own oracle-free correctness check.

The remaining wall — why it stops at 36/48

The 12 unsolved tasks are oracle-blind, not under-leveraged: the deciding fact lives only in the hidden solution / tests, so no prompt-side rule can reach them (answer-selection with no local signal, lying or absent column contracts, conventions erased downstream). Moving past 75% is a benchmark-design change — ship truthful contracts or a subset of the hidden tests — not a smarter prompt.
